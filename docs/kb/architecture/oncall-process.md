# On-call 流程与告警分级

## 告警分级

| 级别 | 定义 | 响应时间 | 示例 |
|------|------|----------|------|
| P0 | 全站不可用，核心链路中断 | 5 分钟 | gateway 宕机、MySQL 主库挂 |
| P1 | 核心功能受损，部分用户受影响 | 15 分钟 | 支付成功率下降 >5%、订单延迟 >10s |
| P2 | 非核心功能异常 | 1 小时 | 搜索排序不准、通知延迟 |

## On-call 值班

- 轮值周期：每人 1 周，周一 10:00 交接
- 工作日：9:00-22:00 主动关注告警
- 非工作日：保持手机畅通，P0/P1 必须响应
- 交接内容：未解决事故、待跟进项、已知风险

## 事故响应流程

```
告警触发 → 确认接收（5min）→ 初步评估 → 止血 → 根因分析 → 恢复 → 复盘
```

### 1. 确认接收
- 在 On-call 群回复「收到，开始排查」
- 超过响应时间未确认，自动升级到 backup On-call

### 2. 初步评估
- 看告警内容：服务名、指标、阈值
- 查 Grafana 对应 Dashboard
- 判断影响范围：多少用户、哪些功能

### 3. 止血（优先恢复服务）
- 优先恢复，不急于找根因
- 常见止血手段：回滚、扩容、降级、切流量
- 止血后记录操作和时间线

### 4. 根因分析
- 查日志：ELK / kubectl logs
- 查监控：事发前后指标变化
- 查变更：最近部署、配置修改

### 5. 恢复
- 确认服务恢复正常指标
- 逐步恢复降级的功能
- 观察稳定性 30 分钟

### 6. 复盘
- P0/P1 事故 48 小时内提交复盘文档
- 格式见 `postmortems/` 目录
- 关注「为什么没更早发现」「怎么防止再发」

## 危险操作清单

以下操作需要 SRE Lead 审批：
- `FLUSHALL` / `FLUSHDB`（Redis 清空）
- `DROP TABLE` / `TRUNCATE`（数据库删表）
- `kubectl delete namespace`（删命名空间）
- 生产环境直接执行 SQL 修改数据
- 修改限流/熔断阈值
